CHAPTER 10.8 - PARCELS_AND_BUILDABLE_AREAS
STATUS: READY

======================================================================
GOAL
======================================================================
Subdivide blocks and rural road frontage into deterministic parcels with explicit frontage, access intent, setbacks and buildable polygons, then exchange stable site requests/resolutions with the building generator while preventing overlaps/road/water conflict.

======================================================================
PUBLIC CONTRACTS
======================================================================
1. Parcel has stable ParcelId, source BlockId or rural road ref, polygon, area,
zone, frontage segment/road, access flag and buildable polygon(s).

Parcel access is explicit semantic data:
    ParcelAccessIntent
        frontage/access point or admissible frontage interval
        required clear width and approach constraints
        semantic access class and surface/kind
    GateSpec
        frontage location / left-right endpoints
        clear width
    DrivewaySpec
        connection from road/access point to parcel/building approach
        semantic access class: Service or Local according profile
        surface/kind: Track for unpaved parcel access
    FenceSpec optional
        fenced flag
        type {Wood, Wire, Wall}
        planned panel spans
        post points
        gate reference

These are not renderer objects.

BuildingSiteRequest is the city-owned boundary DTO. It contains stable request
and ParcelId, seed path, zone, buildable polygon, optional preferred footprint
envelope/orientation, height/storey constraints and ParcelAccessIntent. A box
drawn by a planning/debug view is only a preferred envelope in this request; it
is not a finished building.

BuildingSiteResolution is the return DTO from the buildings module. It contains
the request/parcel IDs, stable BuildingPlanId, resolved footprint, selected
entrance/approach point, clearance envelope and reserved exterior connections.
It intentionally does not expose BuildingPlan internals to the city module.

2. Urban parcel subdivision prioritizes road frontage and target width/depth ranges by zone; residual polygons are either valid residual parcels or explicitly reported.

3. Buildable area = parcel minus setback/ROW/water/protected constraints; operation may return multiple polygons, choose/retain according explicit policy.

4. Rural frontage parcels generated along eligible roads with spacing/depth and spatial hash overlap checks.

5. Fence planning uses the final TARGET contract:
    default panel target length = 2.4 m
    default gate width = 4.2 m, capped by frontage policy
    gate creates a real opening in the front fence
    panel span is rejected if it conflicts with road corridor, another parcel,
    or building footprint clearance
    conflicting spans are shortened, split or omitted deterministically;
    the complete fence is omitted only when no valid layout remains

GateSpec, DrivewaySpec and FenceLayout are finalized only after the city
receives BuildingSiteResolution. Preliminary placeholder rectangles are not
valid substitutes for the resolved footprint and entrance.

6. Access intent is part of parcel/city semantics. Final driveway/gate geometry
is resolved against the returned building entrance and reserves space before
vegetation/fence placement; it is not added later only as visual mesh.

======================================================================
IMPLEMENTATION STEPS
======================================================================
STEP 1
    Define zone-based ParcelProfile target frontage/depth/setbacks.

STEP 2
    Determine block road-facing edges by nearest/corresponding road corridor metadata, not O(all roads) brute force.

STEP 3
    Recursively/sweep split block polygon into frontage parcels with hard min area/width.

STEP 4
    Generate buildable offsets and subtract constraints.

STEP 5
    Generate rural road-oriented OBB/polygon parcels using spatial index.

STEP 6
    Create ParcelAccessIntent and BuildingSiteRequest from each accepted parcel.
    Use a Service or Local access-class intent with Track surface for unpaved
    parcel access.

STEP 7
    Pass BuildingSiteRequest to Stage 11. After BuildingSiteResolution returns,
    finalize the driveway/access reservation from frontage to the actual
    entrance and plan optional fence spans/posts/gate from the parcel boundary.

STEP 8
    Validate containment, overlap, road/water exclusion, access, gate opening,
    fence-road/building/neighbor clearances and driveway continuity.

======================================================================
PSEUDOCODE
======================================================================
URBAN BLOCK:
    frontageEdges := map block edges to road corridors
    candidateCuts := derive widths from profile + seed
    parcels := split polygon along frontage progression
    for p:
        if hard constraints fail: merge/residual policy
        buildable := inset/subtract(p,setbacks,constraints)
        assign stable ParcelId(blockId, frontageOrdinal)
        request := make BuildingSiteRequest(buildable, accessIntent, seedPath)
        resolution := Stage11.resolve(request)
        finalize gate/driveway against resolution.entrance
        plan optional fence after resolved footprint/access reservations

RURAL:
    for road in stable order:
        for station in seeded spacing:
            candidate := oriented parcel
            if index overlap/road/water/outside: reject
            insert

======================================================================
THREADING / OWNERSHIP RULES
======================================================================
Each generation stage reads immutable prior artifacts and writes a candidate output; independent regions/blocks/parcels use jobs with stable IDs and stable merge.

======================================================================
ERROR HANDLING
======================================================================
Invalid candidates are rejected through typed result/ValidationReport; bounded fallback strategies are explicit and traced.

======================================================================
DETERMINISM RULES
======================================================================
Stable seed paths, node/edge IDs and deterministic tie-breakers define output; hash-map/job iteration never does.

======================================================================
PERFORMANCE RULES
======================================================================
Use spatial indexes/fields rather than global scans; batch expensive routing/placement and benchmark large city profiles.

======================================================================
MIGRATION / COMPATIBILITY
======================================================================
There is one TARGET parcel/access/fence behavior. Prototype samples contribute
test cases only; no alternate compatibility planner is implemented.
