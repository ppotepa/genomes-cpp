======================================================================
PUBLIC CONTRACTS
======================================================================
1. Parcel has stable ParcelId, source BlockId or rural road ref, polygon, area,
zone, frontage segment/road, access flag and buildable polygon(s).

Parcel access is explicit semantic data:
    GateSpec
        frontage location / left-right endpoints
        clear width
    DrivewaySpec
        connection from road/access point to parcel/building approach
        semantic access class: Service or Local according profile
        SOURCE compatibility surface/kind: Track
    FenceSpec optional
        fenced flag
        type {Wood, Wire, Wall}
        planned panel spans
        post points
        gate reference

These are not renderer objects.

2. Urban parcel subdivision prioritizes road frontage and target width/depth ranges by zone; residual polygons are either valid residual parcels or explicitly reported.

3. Buildable area = parcel minus setback/ROW/water/protected constraints; operation may return multiple polygons, choose/retain according explicit policy.

4. Rural frontage parcels generated along eligible roads with spacing/depth and spatial hash overlap checks.

5. Fence planning preserves SOURCE FenceGenerator.plan() semantics:
    compatibility panel target length = 2.4 m
    compatibility default gate width = 4.2 m, capped by frontage policy
    gate creates a real opening in the front fence
    panel span is rejected if it conflicts with road corridor, another parcel,
    or building footprint clearance
    all-or-nothing compatibility behavior where SOURCE returns no fence when
    expected panel segmentation cannot be produced is represented in the
    legacy compatibility profile

Native later versions may use more flexible partial-fence recovery, but not
under exact SOURCE fence parity.

6. Driveway/access geometry is part of parcel/city semantics and reserves space
before vegetation/fence placement; it is not added later only as visual mesh.

======================================================================
IMPLEMENTATION STEPS
======================================================================
STEP 1
    Define zone-based ParcelProfile target frontage/depth/setbacks.

STEP 2
    Determine block road-facing edges by nearest/corresponding road corridor metadata, not O(all roads) brute force.

STEP 3
    Recursively/sweep split block polygon into frontage parcels with hard min area/width.

STEP 4
    Generate buildable offsets and subtract constraints.

STEP 5
    Generate rural road-oriented OBB/polygon parcels using spatial index.

STEP 6
    Create driveway/access reservations from frontage/gate to building approach.
    For SOURCE simple-settlement compatibility use an access-class edge
    (Service/Local profile) with surface/kind Track, and reserve it before
    scatter.

STEP 7
    Plan optional fence spans/posts/gate from parcel boundary using SOURCE
    compatibility profile or newer explicit profile.

STEP 8
    Validate containment, overlap, road/water exclusion, access, gate opening,
    fence-road/building/neighbor clearances and driveway continuity.

======================================================================
PSEUDOCODE
======================================================================
URBAN BLOCK:
    frontageEdges := map block edges to road corridors
    candidateCuts := derive widths from profile + seed
    parcels := split polygon along frontage progression
    for p:
        if hard constraints fail: merge/residual policy
        buildable := inset/subtract(p,setbacks,constraints)
        assign stable ParcelId(blockId, frontageOrdinal)
        plan gate/driveway if access required
        plan optional fence after reserved access corridor

RURAL:
    for road in stable order:
        for station in seeded spacing:
            candidate := oriented parcel
            if index overlap/road/water/outside: reject
            insert

======================================================================
THREADING / OWNERSHIP RULES
======================================================================
Each generation stage reads immutable prior artifacts and writes a candidate output; independent regions/blocks/parcels use jobs with stable IDs and stable merge.

======================================================================
ERROR HANDLING
======================================================================
Invalid candidates are rejected through typed result/ValidationReport; bounded fallback strategies are explicit and traced.

======================================================================
DETERMINISM RULES
======================================================================
Stable seed paths, node/edge IDs and deterministic tie-breakers define output; hash-map/job iteration never does.

======================================================================
PERFORMANCE RULES
======================================================================
Use spatial indexes/fields rather than global scans; batch expensive routing/placement and benchmark large city profiles.

======================================================================
MIGRATION / COMPATIBILITY
======================================================================
SOURCE prototypes remain reference labs. TARGET native city may improve geometry while satisfying exported fixtures/invariants.
