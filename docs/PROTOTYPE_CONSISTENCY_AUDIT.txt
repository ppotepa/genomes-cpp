B. MULTIPLE LEGACY RNG DERIVATION FAMILIES

SOURCE has multiple non-identical systems:

    SOURCE::js/core/seededRandom.js
        Mulberry32 stream

    SOURCE::js/buildings/buildingRandom.js

    TARGET 5.1 previously defined LegacyMulberry32 only, which is insufficient
    for exact SOURCE generator parity.

Correction:
    0.5 now freezes separate legacy algorithms.
    5.1 now requires domain-specific derivation adapters and golden vectors.

SOURCE contains overlapping non-identical building definitions.

Confirmed example:

    SOURCE::js/buildings/buildingCatalog.js

    SOURCE::js/buildings/buildingSpec.js
        RURAL_SHED:
            width 2.5..7 m
            depth 2.5..6 m

This cannot be safely "merged" without a product/version decision.

Correction:
    11.1 now requires a SOURCE conflict inventory and explicit provenance.
    11.12 parity must include fixtures for every conflict.
    Target should use separate/versioned semantic profiles where two SOURCE
    concepts must both survive rather than one ambiguous ID.

9. LEGACY MULBERRY STATE-STORAGE DETAIL
======================================================================

L. SOURCE RNG FAMILY IS NOT LITERALLY ONE STATE IMPLEMENTATION

SOURCE::js/core/seededRandom.js:
    this.state += constant
    // state remains JavaScript Number

SOURCE::js/buildings/buildingRandom.js:
    this.state = (this.state + constant) >>> 0

SOURCE::prototypes/procedural-city/index.html:
    a |= 0
    a = (a + constant) | 0

The mixer/output are equivalent for normal bounded generator streams, but an
unqualified statement that all three are "exact uint32 Mulberry32" is stronger
than SOURCE actually guarantees for arbitrarily long streams.

Correction:
    0.5/5.1 now distinguish Core/Building/City legacy adapters.
    Golden vectors must be generated from the actual SOURCE caller.
