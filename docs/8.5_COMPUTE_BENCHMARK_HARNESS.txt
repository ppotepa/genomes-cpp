Create standardized CPU-vs-GPU compute benchmark harness measuring kernel execution, upload, readback and end-to-end latency separately across workload sizes.

PRESERVES
======================================================================
GPU compute is an acceleration/backend service. Authoritative gameplay remains
correct with CPU fallback unless a later chapter explicitly changes that rule.

======================================================================
OUT OF SCOPE
======================================================================
CUDA fast paths and domain-specific kernels introduced by later stages.

======================================================================

======================================================================
PUBLIC CONTRACTS
======================================================================
1. Every benchmark reports backend, GPU adapter/driver/API, CPU, kernel version, element count, bytes, workgroup, queue, repetitions.

2. Metrics separate CPU reference time, GPU dispatch/kernel timestamp, upload, readback and end-to-end wall time.

3. Correctness comparison occurs before timing and after representative runs; benchmark never times invalid output.

4. Sizes use logarithmic/relevant sets and include crossover region where GPU overhead loses to CPU.

======================================================================
DATA LAYOUT
======================================================================
Compute inputs/outputs are explicit buffer/view descriptors with versioned kernel parameter blocks; no backend-native pointer leakage.

IMPLEMENTATION STEPS
======================================================================
STEP 1
    Implement harness registering same semantic KernelId on CPU and Diligent backends.

STEP 2
    Warm pipeline/shader/resource setup outside timed region unless benchmark explicitly measures setup.

STEP 3
    Generate deterministic input once per case.

STEP 4
    Run correctness compare with absolute/relative tolerance declared per kernel.

STEP 5
    Measure CPU, GPU-resident chain, upload+kernel and upload+kernel+readback separately.

STEP 6
    Emit JSON/CSV summary and crossover estimate; no shared-runner regression gate.

======================================================================
PSEUDOCODE
======================================================================
CASE(size):
    input := deterministicData(size)
    cpuExpected := runCpu(input)
    gpuActual := runGpuAndReadback(input)
    assert compare(cpuExpected,gpuActual)

    measure cpuKernel
    measure gpuResidentKernel
    measure uploadPlusKernel
    measure fullRoundTrip

REPORT:
    include metadata + p50/p95 + bytes + backend
    find smallest size where gpuResident < cpu

======================================================================
THREADING / OWNERSHIP RULES
======================================================================
CPU prepares immutable dispatch inputs; backend owns GPU resources and synchronization. Readbacks become visible only after completion tokens/fences.

======================================================================
ERROR HANDLING
======================================================================
Unsupported GPU feature selects explicit CPU/fallback path where allowed; shader/dispatch failures return typed errors and diagnostics.

======================================================================
DETERMINISM RULES
======================================================================
GPU-derived advisory fields may be numerically non-bitwise-identical across hardware; authoritative CPU state cannot depend on undocumented nondeterministic reductions.

======================================================================
PERFORMANCE RULES
======================================================================
Batch dispatches, avoid CPU/GPU ping-pong, measure transfer cost separately from kernel cost and prefer GPU-resident pipelines.

======================================================================
MIGRATION / COMPATIBILITY
======================================================================
TARGET compute service is new infrastructure; SOURCE has no equivalent general
compute layer and remains reference for domain outputs only.
