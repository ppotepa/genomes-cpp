======================================================================
0. PURPOSE
======================================================================

Historical design, research and implementation documentation remains in
SOURCE::docs/. TARGET::docs/ contains the normative final product contracts and
the executable C++ implementation manual. SOURCE documentation is referenced,
not copied wholesale.

The final TARGET contract always takes precedence:
    docs/TARGET_IMPLEMENTATION_CONTRACT.txt

Classification of optional SOURCE evidence is documented separately in:
    docs/SOURCE_PROTOTYPE_AND_MOCKUP_CONTRACT.txt

The numbered X.Y_*.txt files form one roadmap with two chapter classes:

    STAGE 0 (0.1-0.6)
        normative/meta/reference chapters.
        They constrain implementation but are not source-code tasks by
        themselves.

    STAGES 1-22
        executable implementation chapters that an agent can implement
        chapter-by-chapter.

Together they define the complete final implementation manual. SOURCE material
informs capability coverage but does not define runtime architecture.

The intended usage is:

    "Implement docs/1.1_CPP_CMAKE_BOOTSTRAP.txt in this repository."

An implementation agent must be able to execute that chapter without inventing
architecture that belongs in later chapters.

======================================================================
1. NON-NEGOTIABLE MIGRATION RULE
======================================================================

GENOMES IS MIGRATED AND IMPROVED, NOT RESET.

Existing systems remain requirements until a chapter explicitly migrates them:

    current browser runtime
    deterministic seeded generation
    infantry genome/anatomy/appearance
    procedural animation and IK
    equipment and weapon systems
    vegetation and rock generators
    current building runtime
    destruction and rubble
    ballistics
    AI experiments
    world runtime
    procedural-city prototype
    procedural-road-graph prototype
    procedural-building-generator prototype
    tests, fixtures and research documentation

SOURCE may continue to exist as a separate prototype/evidence repository, but
it never defines an alternate native production path. Each accepted capability
must have a TARGET owner and measurable validation.

NO chapter may silently drop an existing feature because it is inconvenient to
implement.

2. FILE NAMING
======================================================================

Roadmap chapter:

Implementation-executable chapters begin at Stage 1.

Examples:

    docs/0.1_TARGET_ARCHITECTURE.txt   # normative/meta
    docs/1.1_CPP_CMAKE_BOOTSTRAP.txt  # executable
    docs/1.1_CPP_CMAKE_BOOTSTRAP.txt
    docs/1.2_THIRD_PARTY_DEPENDENCIES.txt
    docs/2.1_STRONG_IDS_RESULT_HASH.txt

X = stage / milestone.
Y = ordered chapter inside the stage.

A chapter may only assume files listed in its REQUIRES section are complete.

    OUTPUT / HANDOFF TO NEXT CHAPTER

If a section is not applicable, the chapter says "N/A" and explains why.

STAGE 0 FORMAT EXCEPTION
------------------------

0.1-0.6 are normative/meta/reference chapters. Their structure may be
specialized to their purpose (for example 0.5 is a mathematical reference
registry) and they do not need artificial implementation-only sections merely
to satisfy formatting.

They MUST still be internally complete, versioned, STATUS-tracked and provide
the contracts/references/acceptance information appropriate to their role.

No Stage 1+ implementation chapter gets this exception.

======================================================================
4. AGENT EXECUTION CONTRACT
======================================================================

When told to implement one chapter, the agent must:

1. Read that complete chapter.
2. Read every file listed under REQUIRES / EXISTING REFERENCES.
3. Inspect relevant TARGET/SOURCE repository state before editing.
4. Implement ALL chapter steps, not a subset.
5. Do not implement future chapters unless required to make the current
   chapter compile/test and the chapter explicitly permits the minimal bridge.
6. Do not omit an accepted product capability unless the owning TARGET chapter
   records an explicit rejection/replacement decision.
7. Add all tests required by the chapter.
8. Run all commands listed in COMMANDS TO RUN that are possible in the
   environment.
9. Re-read the chapter after implementation and check every completion item.
10. If an item is incomplete, continue implementing instead of reporting
    success.
11. Update only documentation/status files explicitly permitted by the chapter.
12. Return the exact changed files, tests executed, results, and remaining
    blockers.
13. For every nontrivial mathematical or algorithmic implementation, resolve
    the required MATH-*, ALG-* and REF-* IDs from:
        docs/0.5_MATHEMATICAL_NOTATION_AND_ALGORITHM_REFERENCE.txt
14. If a required definition is missing, add a canonical referenced definition
    to 0.5 before the implementation chapter may be considered READY.
15. Do not silently invent a different version of an algorithm when the manual
    specifies a canonical reference ID.

"Mostly done" is not chapter complete.

======================================================================
5. STATUS VALUES
======================================================================

PLANNED
    title and place in roadmap exist, chapter not yet authored.

DRAFT
    implementation instructions exist but completeness review is pending.

READY
    chapter has enough detail to hand directly to an implementation agent.

IMPLEMENTED
    repository implementation and required tests satisfy acceptance criteria.

SUPERSEDED
    replaced by a newer explicitly referenced chapter.

The status written in a chapter is documentation status, not proof that code is
implemented. A chapter becomes IMPLEMENTED only after verification.

======================================================================
6. COMPLETENESS RULE
======================================================================

A chapter is considered READY only when an implementation agent should not have
to make a major architectural decision.

The chapter must provide pseudocode for:
    initialization/entry points,
    core algorithms,
    ownership/lifetime,
    important loops,
    job boundaries,
    error paths,
    tests,
    compatibility bridges.

The agent may choose syntax details and obvious local implementation details.
The agent should NOT have to decide subsystem boundaries, ownership model,
threading model, file locations, public interfaces, migration strategy or
acceptance criteria.

======================================================================
8. MASTER COMPLETENESS MATRIX
======================================================================

For each chapter we will track:

    [ ] chapter authored
    [ ] pseudocode complete
    [ ] mathematical contracts complete or explicitly N/A
    [ ] algorithm reference IDs complete or explicitly N/A
    [ ] primary/source references complete or explicitly N/A
    [ ] existing-system references complete
    [ ] file tree complete
    [ ] tests specified
    [ ] acceptance criteria measurable
    [ ] forbidden shortcuts specified
    [ ] dependencies explicit
    [ ] final TARGET policy and validation defined
    [ ] reviewed against overall architecture

Only after every applicable check may chapter STATUS become READY.

For mathematics-heavy chapters, "pseudocode complete" additionally means:
    - equations use the canonical notation from 0.5,
    - numerical tolerances/predicates are explicit,
    - deterministic tie-breaking is explicit,
    - algorithm INPUT/OUTPUT/PRECONDITIONS/POSTCONDITIONS are specified,
    - complexity variables are defined,
    - failure/degenerate cases are specified.

======================================================================
9. WHY THIS MANUAL EXISTS
======================================================================

The goal is not merely to document the desired architecture.

The goal is to make the documentation precise enough that successive AI agents
can implement the engine in small verified chapters while preserving continuity
and avoiding a rewrite that accidentally loses existing Genomes functionality.

This file is the authoritative index for the new implementation manual.
