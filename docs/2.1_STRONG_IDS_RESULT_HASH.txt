CHAPTER 2.1 - STRONG IDS, RESULT, AND STABLE HASH
STATUS: READY
VERSION: 0.1

======================================================================
GOAL
======================================================================

Implement the first reusable Foundation primitives:

    - strongly typed stable IDs,
    - generation-safe runtime handles,
    - C++20 Result<T,E>,
    - canonical stable 64-bit semantic hashing primitives.

These primitives become dependencies of:

    jobs
    procedural generation
    world/regions
    ECS
    artifacts
    navigation
    rendering handles
    physics handles

The implementation must avoid:

    accidental ID-type mixing,
    std::hash as persisted/deterministic identity,
    exception-driven normal control flow,
    invalid stale runtime handles,
    hidden allocations in common Result/ID paths.

======================================================================
PUBLIC CONTRACTS
======================================================================

1. StrongId

Concept:

    template<class Tag, class Rep = std::uint64_t>
    class StrongId;

Properties:

    explicit construction from Rep
    equality/ordering
    value()
    invalid/default value = 0
    isValid()
    no implicit conversion between ID types
    trivially copyable target
    standard-layout target
    no allocation

Example tags:

    struct EntityIdTag;
    struct RegionIdTag;

Aliases themselves should live in owning modules later:

    using EntityId = StrongId<EntityIdTag>;

Foundation should not declare domain-specific tags unless needed by foundation.


2. Handle

Runtime generational handle:

    template<class Tag>
    struct Handle
    {
        std::uint32_t index;
        std::uint32_t generation;
    };

Invalid:

    index      = UINT32_MAX
    generation = 0

Properties:

    equality
    validity
    stable packing to uint64 if needed

This is for ephemeral runtime slot identity, NOT persisted semantic identity.


3. Result<T,E>

C++20 value-or-error type.

Required:

    Result<T,E>::success(T)
    Result<T,E>::failure(E)
    hasValue()
    operator bool()
    value()
    error()

No implicit conversion from T/E if ambiguity can occur.

Accessing wrong alternative in Debug:
    assertion / contract diagnostic.

In Release:
    behavior must still be defined; preferred explicit terminate/assert helper or
    checked access implementation.

Do not throw for expected generator failures.


4. Result<void,E>

Required specialization.

Used for operations with no success payload.


5. Error

Foundation error descriptor must be compact:

    enum class ErrorCode : uint32_t

    struct Error
    {
        ErrorCode code;
        std::string_view message;
    };

Do not add owning std::string to every hot-path Error yet.

Detailed dynamic context can be layered later by diagnostic systems.


6. StableHash64

Distinct from std::hash.

Required APIs:

    uint64_t stableHashBytes(span<const byte>)
    uint64_t stableHashString(string_view)
    uint64_t stableHashU64(uint64_t)
    uint64_t stableHashCombine(uint64_t seed, uint64_t value)

Contract:
    same byte sequence + same algorithm version -> same result across supported
    platforms.

Never hash raw object memory for semantic identity unless representation is
explicitly canonicalized byte-for-byte.


7. HASH VERSION

Define:

    StableHashAlgorithmVersion = 1

Later persistence/artifact systems record algorithm version where hashes survive
process boundaries.

Do not prematurely implement a hand-written union unless profiling or compile
requirements justify it.

======================================================================
MATHEMATICAL CONTRACTS
======================================================================

Deterministic hash identity is discrete, not approximate.

No floating approximate comparison applies.

Canonical combine is order-sensitive:

    H(a,b) != assumed equal H(b,a)

unless collision occurs.

======================================================================
IMPLEMENTATION STEPS
======================================================================

STEP 1 - StrongId.hpp

Implement:

    template<class Tag, class Rep = uint64_t>
    class StrongId final

Pseudo-interface:

    constexpr StrongId() noexcept = default;

    explicit constexpr StrongId(Rep v) noexcept
        : value_(v) {}

    [[nodiscard]]
    constexpr Rep value() const noexcept;

    [[nodiscard]]
    constexpr bool isValid() const noexcept
    {
        return value_ != 0;
    }

    explicit constexpr operator bool() const noexcept;

    auto operator<=>(...) const = default;

Do NOT provide:
    implicit Rep conversion,
    arithmetic operators,
    cross-tag constructor.


STEP 2 - compile-time tests

static_assert:
    trivially_copyable
    standard_layout
    size target
    EntityId-like tag not constructible from another tag type


STEP 3 - Handle.hpp

Implement:

    template<class Tag>
    struct Handle final
    {
        uint32_t index = InvalidIndex;
        uint32_t generation = 0;

        isValid()
        packed()
        equality/order if useful
    };

packed():

    (uint64_t(generation) << 32)
    | uint64_t(index)

Do not interpret packed value as persistent semantic ID.


STEP 4 - stale handle test model

Test miniature slot table semantics:

    create slot generation 1
    acquire handle {index,1}
    destroy increments generation
    old handle fails generation check
    new handle {index,2} validates

Actual slot table is not implemented here.


STEP 5 - Error.hpp

Define small error taxonomy sufficient for foundation tests:

    None
    InvalidArgument
    InvalidState
    NotFound
    OutOfRange
    Unsupported
    Internal

Later modules may define richer domain enums or error payloads.


STEP 6 - Result.hpp

Preferred C++20 implementation:

    std::variant<T,E>

Factories:

    static success(T)
    static failure(E)

Observers:

    bool hasValue() const noexcept
    explicit operator bool() const noexcept

Accessors:
    T& value()
    const T& value() const
    E& error()
    const E& error() const

Move-only T must work.

Do not require T to be copyable.


STEP 7 - Result<void,E>

Represent with:

    bool success_
    E error_

or equivalent optional/variant structure.

Default construction policy must be explicit.

Preferred:
    no ambiguous implicit "success by default".

Factory use only:
    success()
    failure(error)


STEP 8 - StableHash

Chapter 2.1 freezes a simple deterministic 64-bit semantic hash primitive.

Use canonical byte hash:

    FNV-1a 64-bit

Constants:

    offset_basis = 14695981039346656037
    prime        = 1099511628211

For each byte b in exact byte order:

    hash = hash XOR uint64(b)
    hash = hash * prime          // uint64 wraparound is intentional

Then apply no hidden platform-dependent transformation.

This choice is for:
    stable semantic keys,
    labels,
    small IDs,
    reproducibility.

It is NOT selected as:
    cryptographic hash,
    high-throughput artifact content hash,
    adversarial hash-table defense.

Later artifact/cache chapter may introduce XXH3/BLAKE3 or another separately
versioned content hash without changing StableHash64 v1.


STEP 9 - U64 CANONICAL BYTES

stableHashU64(value) MUST NOT hash host-memory byte order.

Canonical byte order:
    little-endian semantic encoding.

Pseudocode:

    bytes[0] = (value >> 0)  & 0xff
    ...
    bytes[7] = (value >> 56) & 0xff

Then stableHashBytes(bytes).


STEP 10 - HASH COMBINE

Do NOT concatenate host structs.

Define:

    stableHashCombine(seed, value):
        encode seed as canonical 8 bytes
        encode value as canonical 8 bytes

        hash := FNV_offset_basis
        feed bytes(seed)
        feed bytes(value)

        return hash

Later SeedTree may hash more explicit tuple fields with length delimiters.


STEP 11 - STRING HASH

Hash exact UTF-8 bytes of std::string_view.

No locale.
No case folding.
No Unicode normalization.

If semantic normalization is required, owning subsystem normalizes BEFORE hash.


STEP 12 - TEST FIXTURES

Freeze exact expected hashes for:

    empty byte sequence
    "Genomes"
    "terrain"
    "building"
    0
    1
    UINT64_MAX
    combine(0,0)
    combine(hash("city"), 42)

Expected values must be generated once from an independent/reference
implementation and committed in tests.

Do not make tests calculate expected values with the same function under test.

Cases:

======================================================================
PSEUDOCODE
======================================================================

STRONG ID:

    template Tag, Rep:
        value := 0

        constructor(rep):
            value := rep

        isValid():
            return value != 0


GENERATION HANDLE VALIDATION:

    function validate(handle, slot):
        if !handle.isValid:
            return false

        if handle.index >= slots.size:
            return false

        return slots[handle.index].generation == handle.generation


RESULT:

    function successful(value):
        result.storage := ValueAlternative(value)
        return result

    function failed(error):
        result.storage := ErrorAlternative(error)
        return result


FNV1A64:

    function stableHashBytes(bytes):
        h := 14695981039346656037

        for each byte b in bytes:
            h := h XOR uint64(b)
            h := h * 1099511628211
            // unsigned 64-bit overflow wraps modulo 2^64

        return h


U64 CANONICALIZATION:

    function encodeLE64(x):
        for i in [0,8):
            bytes[i] := byte((x >> (8*i)) & 0xff)

        return bytes

======================================================================
THREADING / OWNERSHIP RULES
======================================================================

All primitives are thread-safe by value.

No internal shared mutable state.

StableHash functions are pure.

StrongId/Handle are POD-like values.

Result owns only its payload/error according to T/E ownership.

======================================================================
ERROR HANDLING
======================================================================

Result is the expected-error mechanism for future APIs.

Exceptions:
    not used for ordinary generation/query failure.

Programmer contract violation:
    assertion/diagnostic policy from 2.3 later.

Until 2.3 exists:
    use standard assert only internally where unavoidable,
    tests must not rely on undefined wrong-alternative access.

======================================================================
DETERMINISM RULES
======================================================================

std::hash is forbidden for:
    persisted IDs,
    seed derivation,
    deterministic artifacts,
    network/save identity,
    parity fixtures.

StableHash64 v1 is byte-defined.

Never hash:
    pointer value,
    object address,
    padding bytes,
    platform-native size_t encoding,
    unordered container iteration order.

======================================================================
PERFORMANCE RULES
======================================================================

StrongId and Handle:
    zero-overhead wrappers target.

Result:
    no heap required by wrapper itself.

Hash:
    FNV1a is accepted for small semantic keys.
    Do not use it blindly for multi-megabyte artifact hashing later.

======================================================================
MIGRATION / COMPATIBILITY
======================================================================

Legacy JS IDs/hashes remain.

Migration chapters explicitly map:
    legacy numeric/string ID
    -> native StrongId

When exact legacy hash is part of behavior:
    implement legacy hash as a separately named compatibility function.

Do NOT overload StableHash64 v1 with legacy quirks.
