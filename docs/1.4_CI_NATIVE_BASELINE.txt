CHAPTER 1.4 - NATIVE CI BASELINE
STATUS: READY
VERSION: 0.1

======================================================================
GOAL
======================================================================

Add a native continuous-integration baseline that proves the Stage 1 native
skeleton can be built from a clean checkout with pinned submodules and without
breaking the existing legacy/browser CI.

After this chapter:

    - native CMake configure/build/test runs in CI,
    - submodules are checked out recursively,
    - Debug and Release configurations are exercised,
    - native correctness tests run through CTest,
    - legacy CI remains separate and intact,
    - failures clearly identify native-vs-legacy responsibility.

======================================================================
IMPLEMENTATION STEPS
======================================================================

STEP 1 - INSPECT EXISTING WORKFLOW

Read SOURCE::.github/workflows/destruction-building-ci.yml as reference.

Do not copy its Node/browser setup into TARGET native CI.


STEP 2 - CREATE native-ci.yml

Triggers:

    pull_request
    push to main
    workflow_dispatch

Do not run on every irrelevant branch push unless repository policy requires it.


STEP 3 - CHECKOUT

Use official checkout action.

Required behavior:

    fetch repository
    initialize submodules recursively

Concept:

    submodules: recursive


STEP 4 - TOOLCHAIN DISCOVERY

For each job, print:

    cmake --version
    compiler --version

Linux:
    use runner-provided GCC or Clang chosen explicitly.

Windows:
    use MSVC developer environment supported by CMake generator/preset.

Do not rely on accidental shell defaults without logging them.


STEP 5 - LINUX DEBUG

Configure:
    native Debug

Build:
    all Stage 1 native targets

Test:
    ctest --output-on-failure

Warnings-as-errors:
    ON for Genomes code.


STEP 6 - LINUX RELEASE

Clean configure/build.

Run CTest correctness suite.

Do not treat microbenchmark timings on shared GitHub runners as stable
performance gates.


STEP 7 - WINDOWS DEBUG

Configure/build/test with MSVC.

Warnings-as-errors:
    ON for Genomes-owned code.


STEP 8 - WINDOWS RELEASE

Configure/build/test.

Run genomes_headless as post-build smoke.

Expected output contains exactly:

    Genomes native 0.1


STEP 9 - TEST FAILURE VISIBILITY

CTest command must use:

    --output-on-failure

Do not swallow exit codes.

Do not use:
    continue-on-error: true

for required build/test steps.


STEP 10 - LEGACY WORKFLOW PRESERVATION

Do not modify legacy workflow unless the native bootstrap genuinely requires a
shared repository setup fix.

After native workflow creation, ensure the SOURCE workflow still exists in SOURCE.
TARGET does not need a duplicate legacy workflow.


STEP 11 - DEPENDENCY FAILURE BEHAVIOR

If recursive submodule checkout fails:
    job fails.

Do not silently fall back to downloading moving dependency versions.


STEP 12 - OPTIONAL BUILD CACHE

Only after cold workflow succeeds.

Cache keys must include enough identity to avoid cross-revision corruption,
e.g.:

    OS
    compiler
    build config
    dependency/submodule state or lock-relevant hash

Cache is optimization only.


STEP 13 - NO PERFORMANCE GATE YET

Google Benchmark executables may be compiled in Release.

Do NOT fail CI based on shared-runner timing.

Performance regression gates belong to controlled benchmark infrastructure in
Stage 22.


STEP 14 - LOCAL REPRODUCTION

Every CI configure/build/test command must be reproducible locally using the
same CMake presets or clearly documented equivalent command.

CI must not contain hidden build semantics unavailable to developers.


======================================================================
PSEUDOCODE
======================================================================

WORKFLOW:

    on:
        pull_request
        push(main)
        workflow_dispatch

    matrix:
        linux/debug
        linux/release
        windows/debug
        windows/release

    for each configuration:
        checkout(recursiveSubmodules = true)

        printToolVersions()

        configure(configuration)

        build(configuration)

        test(
            configuration,
            outputOnFailure = true
        )

        if configuration == windows/release:
            runHeadlessSmoke()


CI FAILURE POLICY:

    if configure fails:
        FAIL

    if build fails:
        FAIL

    if required CTest fails:
        FAIL

    if headless smoke output mismatches:
        FAIL

    benchmark timing regression:
        NOT EVALUATED in Stage 1

======================================================================
THREADING / OWNERSHIP RULES
======================================================================

N/A for engine runtime.

CI may use parallel compiler jobs.

Do not infer simulation-thread correctness from parallel build success.

======================================================================
ERROR HANDLING
======================================================================

Workflow steps must preserve process failure codes.

Submodule missing:
    fail with checkout/configure error.

Test failure:
    show CTest output.

No required step may be masked by:
    || true
    continue-on-error
    shell error suppression.

======================================================================
DETERMINISM RULES
======================================================================

CI correctness tests use fixed/reported seeds where randomness exists.

Later determinism jobs will explicitly vary worker counts.

Stage 1 has no simulation determinism matrix yet.

======================================================================
PERFORMANCE RULES
======================================================================

Shared hosted-runner wall-clock timing is diagnostic only.

Do not store hosted-runner microbenchmark values as hard performance budgets.

Compilation/cache performance does not define runtime performance.

======================================================================
MIGRATION / COMPATIBILITY
======================================================================

Legacy SOURCE CI and native TARGET CI coexist in separate repositories.

Native failure:
    does not justify disabling legacy CI.

Legacy failure:
    does not justify marking native migration complete.

Both suites contribute to repository health during migration.

COMMANDS TO RUN

Run headless.
