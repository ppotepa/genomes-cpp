CHAPTER 8.3 - ASYNC_COMPUTE_SCHEDULING
STATUS: READY

======================================================================
GOAL
======================================================================
Add queue-aware scheduling so independent compute workloads can overlap graphics where hardware/backend allows without assuming async compute is always faster.

======================================================================
PUBLIC CONTRACTS
======================================================================
1. QueueClass = Graphics, Compute, Transfer. Pass expresses preference/requirement; graph compiler may collapse to Graphics if separate queue unavailable.

2. Cross-queue dependency emits explicit fence/semaphore ownership synchronization; logical resource hazards remain graph-derived.

3. AsyncComputePolicy can disable globally, whitelist kernels/passes, or enable Auto benchmark-informed mode.

4. No correctness depends on overlap. Same graph executes serially on one queue.

======================================================================
DATA LAYOUT
======================================================================
Compute inputs/outputs are explicit buffer/view descriptors with versioned kernel parameter blocks; no backend-native pointer leakage.

STEP 3

======================================================================
PSEUDOCODE
======================================================================
ASSIGN QUEUE:
    for pass in topo:
        if pass.prefersCompute
           and caps.separateCompute
           and policy.allows(pass)
           and estimatedSyncCost acceptable:
            queue := Compute
        else:
            queue := Graphics

CROSS QUEUE EDGE:
    producer.signal(fenceValue)
    consumer.wait(fenceValue)
    transition ownership/state as backend requires

======================================================================
THREADING / OWNERSHIP RULES
======================================================================
CPU prepares immutable dispatch inputs; backend owns GPU resources and synchronization. Readbacks become visible only after completion tokens/fences.

======================================================================
ERROR HANDLING
======================================================================
Unsupported GPU feature selects explicit CPU/fallback path where allowed; shader/dispatch failures return typed errors and diagnostics.

======================================================================
DETERMINISM RULES
======================================================================
GPU-derived advisory fields may be numerically non-bitwise-identical across hardware; authoritative CPU state cannot depend on undocumented nondeterministic reductions.

======================================================================
PERFORMANCE RULES
======================================================================
Batch dispatches, avoid CPU/GPU ping-pong, measure transfer cost separately from kernel cost and prefer GPU-resident pipelines.

======================================================================
MIGRATION / COMPATIBILITY
======================================================================
TARGET compute service is new infrastructure; SOURCE has no equivalent general
compute layer and remains reference for domain outputs only.
