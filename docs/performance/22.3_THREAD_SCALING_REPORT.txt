SCOPE
----------------------------------------------------------------------
The portable gate library runs the same deterministic workload seed at each
worker count, measures complete callbacks (including merge/barrier work), and
checks semantic hashes before accepting performance data.  It does not impose
linear speedup: each worker count is compared only with its own machine-keyed
baseline and explicit median/p95 limits.

PUBLIC IMPLEMENTATION
----------------------------------------------------------------------
tools/benchmark/thread_scaling_gate.hpp/.cpp provide deterministic seeded
sampling, warmups, median/p95/p99 and variance statistics, strict versioned
baseline JSON parsing, exact machine/compiler/dependency matching, scheduler
telemetry fields, correctness status, and text/JSON reports.  The
genomes_thread_scaling_gate CLI executes deterministic_job_batch_v1 on the
shared jobs::JobSystem implementation, reusing one pool for each worker count.
It submits 64 fixed partitions of 2048 items, with 64 integer mixing rounds
per item, then XOR-reduces partial results after the group completes.
The seed is identical across warmups, repetitions and worker counts.
Timing includes submission, execution, helping wait and reduction; it excludes
pool creation/shutdown and output buffer allocation. Worker counts mean pool
threads; the submitting thread may help while waiting, as in the application.
No dedicated IO worker is created. Steals are measured from scheduler telemetry;
the other optional telemetry fields are not measured by this workload.
Text/JSON include timing and semantic hashes. JSON also includes the seed,
raw measured samples and any error. Failed gates still write --report output.

GATE POLICY
----------------------------------------------------------------------
Matching baselines become hard gates.  Unknown fingerprints report
no_baseline; semantic hash mismatch is correctness_failure; excessive
coefficient of variation is noisy_run; median and p95 limits produce an
explicit regression.  Expected qualitative trend is retained as metadata and
is not converted into an unjustified speedup requirement.

FOCUSED EVIDENCE
----------------------------------------------------------------------
tests/native/stress/thread_scaling_smoke.cpp covers percentile calculation,

workload that still passes its per-worker budgets. It also runs the actual CLI
workload on serial and 1/2/4-worker schedulers and compares their hashes.
These are native concurrency checks; JavaScript parity is not an acceptance gate.

LIMITS
----------------------------------------------------------------------
The checked-in numbers are a deterministic parser/test fixture, not a claim
about every host. Its machine class is synthetic-gate-fixture; the CLI default
is unclassified. Workload IDs agree, but the fixture intentionally cannot act
as a hardware timing baseline for a normal CLI invocation.
Dedicated runners must record refreshed profiles before
enabling a production timing gate; hosted CI should use the smoke/scaling
shape policy.
