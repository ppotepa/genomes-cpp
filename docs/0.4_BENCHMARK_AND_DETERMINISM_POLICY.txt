CHAPTER 0.4 - BENCHMARK AND DETERMINISM POLICY
STATUS: READY

======================================================================
GOAL
======================================================================

Define one benchmark, telemetry and determinism policy for every native Genomes
subsystem before implementation begins.

This chapter prevents invalid comparisons such as:

    "new code feels faster",
    comparing Debug to Release,
    comparing different semantic workloads,
    comparing 1-thread and N-thread versions that do different work,
    hiding queue/drain cost outside the measured interval,
    declaring determinism from one run,
    treating browser FPS as a CPU subsystem benchmark,
    treating one average time as sufficient evidence.

Every later performance-sensitive chapter must use these rules.

PUBLIC CONTRACTS
======================================================================

BENCHMARK LEVELS:

BENCH-MICRO
    One primitive or tight algorithm.
    Example:
        orient2d batch
        BVH query
        RNG throughput

BENCH-SUBSYSTEM
    Complete subsystem operation.
    Example:
        generate 1000 BuildingPlans
        100k spatial radius queries
        one physics fixed tick

BENCH-SCENARIO
    Several real subsystems interacting.
    Example:
        10k units + perception + movement + projectiles

BENCH-STRESS
    Capacity / degradation test.
    Not necessarily a normal gameplay target.

A chapter must name which level it measures.


DETERMINISM LEVELS:

DET-EXACT
    Exact equality of canonical semantic serialization/hash.

Use for:
    integer/topological artifacts,
    IDs,
    deterministic event ordering,
    selected generator fixtures when native algorithm is intentionally exact.

DET-NUMERIC
    Same semantic result with explicitly defined numeric tolerance.

Use for:
    floating geometric quantities where bitwise equality is not required.

DET-INVARIANT
    Exact shape may differ, but all named invariants and stable semantic rules
    must hold for the same generator version.

DET-BEHAVIOR
    Same externally observable state-transition contract.

DET-NONAUTHORITATIVE
    Bitwise/numeric determinism not required.

Use for:
    VFX,
    presentation-only particles,
    timing-dependent visual-only GPU work.

Every subsystem chapter must declare one or more levels.


RULE-BENCH-001
    Benchmark semantic workload is immutable inside one comparison.

Changing:
    entity count,
    seed,
    geometry detail,
    physics settings,
    output validation,
    drain policy

creates a different benchmark case/version.


RULE-BENCH-002
    Measured interval includes all work necessary to produce the claimed result.

Forbidden:
    queue expensive jobs inside measured loop,
    drain them after timer,
    claim only queue-submit cost as subsystem cost.

Queue-submit time may be separately reported, but must be labelled.


RULE-BENCH-003
    Warm-up is explicit.

For native code:
    execute enough setup iterations to populate expected caches and stabilize
    one-time initialization before steady-state timing.

Also separately benchmark cold-start when startup latency matters.


RULE-BENCH-004
    Release/optimized build is required for performance claims.

Debug builds may be used for correctness only.


RULE-BENCH-005
    Run under debugger = invalid performance baseline.


RULE-BENCH-006
    Validation may be outside the timed interval only if:
        it does not alter workload behavior,
        all output is validated after timing,
        benchmark description says so.

If validation itself is part of real runtime behavior, keep it inside.


RULE-BENCH-007
    Each sample distribution reports at minimum:

        sampleCount
        mean
        min
        p50
        p95
        p99
        max

For throughput:
        itemsPerSecond or ticksPerSecond

For fixed simulation:
        simulatedSeconds
        wallSeconds
        realTimeFactor


RULE-BENCH-008
    Never call a one-run max a stable regression metric.

Use percentile/budget policy plus repeated benchmark runs where variance matters.

1. HARDWARE FINGERPRINT
======================================================================

Every benchmark baseline records at least:

    CPU model
    logical threads
    total RAM
    OS

    git commit

A result missing critical hardware metadata is diagnostic evidence, not a

======================================================================
2. CPU BENCHMARK EXECUTION
======================================================================

Canonical procedure:

    configure optimized native build

    create deterministic dataset from:
        benchmarkVersion
        seed
        explicit workload parameters

    initialize subsystem

    run warmup

    for repetition in benchmarkRepetitions:
        reset to same semantic initial state

        for measured iteration:
            start = highResolutionClock()

            execute COMPLETE benchmark operation

            end = highResolutionClock()

            samples.push(end-start)

        validate semantic outputs

    compute distribution
    emit JSON

Do not rebuild a semantically different random dataset between worker counts.

3. MULTICORE SCALING
======================================================================

Every CPU-heavy parallel subsystem gets a scaling run.

Required worker counts when hardware supports them:

    1
    2
    4
    8
    then powers/meaningful points up to available worker count

On 16 logical workers:

    1,2,4,8,16

On 24:

    1,2,4,8,12,16,24

Exact topology-aware cases may later separate:
    physical cores
    SMT threads

Report:
    T1
    Tp
    speedup
    efficiency

Do not reserve different amounts of work at different worker counts.

======================================================================

Run same:
    build
    version
    seed
    inputs

    workerCount = 1
    workerCount = 2

DET TEST PSEUDOCODE:

    baseline := run(case, workers=1, scheduleSeed=0)

    for workers in workerCounts:
        for scheduleSeed in stressScheduleSeeds:

                baseline,

A failure is never dismissed as "thread timing".

======================================================================
6. CANONICAL SEMANTIC HASH
======================================================================

DET-EXACT systems may use canonical hashes.

Rules:

    serialize fields in defined stable order;
    sort unordered semantic sets by stable ID;
    encode integers with explicit width;
    normalize enum encoding;
    define floating-point policy before hashing;
    include schema/generator version.

Do NOT hash:
    raw struct memory,
    pointer addresses,
    padding,
    unordered_map bucket order,
    backend object handles.


PSEUDOCODE:

    function hashRoadGraph(graph):
        nodes := sort(graph.nodes, by StableNodeId)
        edges := sort(graph.edges, by StableEdgeId)

        hasher.add(schemaVersion)

        for node in nodes:
            hasher.add(node.id)
            hasher.add(canonicalPosition(node.position))
            hasher.add(node.semanticType)

        for edge in edges:
            hasher.add(edge.id)
            hasher.add(edge.a)
            hasher.add(edge.b)
            hasher.add(edge.roadClass)

        return hasher.finish()

======================================================================
7. NUMERIC DETERMINISM
======================================================================

DET-NUMERIC comparison must name tolerances per quantity.

Use NUM-SCALE-001 where appropriate.

Bad:
    "results are close enough"

Good:
    position:
        absTol = 1e-5 m
        relTol = 1e-6

But exact values belong to domain chapters.

Topology is never accepted merely because positions are numerically close if
the topology changed and topology is required to remain exact.

======================================================================
8. CROSS-PLATFORM POLICY
======================================================================

Initial mandatory determinism target:

    same supported native build semantics,
    same generator/simulation version,
    same inputs,
    independent of worker count and scheduling.

Cross-compiler / cross-CPU bitwise floating determinism is NOT automatically
promised in Stage 0.

Later networking/lockstep requirements may raise this target.

However:
    integer IDs,
    graph topology,
    deterministic ordering,
    seed derivation

SHOULD be designed to remain portable whenever possible.

Do not accidentally make scheduler nondeterminism part of the model merely
because cross-platform bitwise floating behavior is not yet required.

======================================================================
9. MEMORY BENCHMARK POLICY
======================================================================

Report separately where available:

    process RSS
    committed/resident memory
    subsystem persistent bytes
    cache bytes
    scratch/arena high-water
    allocation count
    peak dynamic entity count

GPU later:
    allocated VRAM
    resident resource bytes if backend provides
    transient render graph high-water
    staging/upload bytes

Do not sum overlapping counters.

Example:
    cache bytes that are already included in process RSS are not "total memory"
    to add again.

Heap delta before/after is NOT proof of no leak.

Leak/lifetime testing is separate.

======================================================================
10. GPU BENCHMARK POLICY
======================================================================

Do not infer GPU cost from CPU render-submit time.

GPU passes use:
    GPU timestamp queries
    backend profiler
    PIX/RenderDoc or equivalent diagnostic tools as appropriate

Report:
    CPU frame time
    simulation CPU
    presentation/extraction CPU
    render submission CPU
    GPU frame
    key GPU pass timings

When async compute is enabled:
    also report overlap and total frame critical path.

A 2 ms compute pass running fully overlapped is not equivalent to adding 2 ms to
frame critical path.


GPU CASE MUST STATE:
    resolution
    MSAA
    quality
    visibility/camera
    object counts
    backend
    vsync/present setting

======================================================================
11. CPU/GPU TRANSFER BENCHMARKING
======================================================================

Compute chapters must measure:

    upload bytes/frame
    readback bytes/frame
    number of synchronization points
    dispatch count
    CPU wait time
    GPU queue wait time where observable

Forbidden claim:
    "GPU version is faster"

if result timing ignores mandatory readback needed by the CPU consumer.

Measure end-to-end path.

13. BASELINE POLICY
======================================================================

A baseline is approved only when:

    semantic validation passes;
    benchmark metadata is complete;
    build is optimized;
    workload version is frozen;
    multiple runs do not show pathological instability.

Baselines live under:

    benchmarks/baselines/<benchmark-id>/<machine-class-or-reference>.json

Early chapters may store one developer reference baseline.
Production CI later decides reference machine classes.

======================================================================
14. REGRESSION POLICY
======================================================================

Early migration:
    record metrics first;
    do not invent arbitrary hard budgets.

Once subsystem workload stabilizes:
    responsible chapter defines:
        warning threshold
        failure threshold

Prefer percentile budgets.

Example concept only:

    p95 regression > 10% -> warning
    p95 regression > 20% -> failure

DO NOT adopt these example numbers globally.
Each mature benchmark defines its own noise envelope and budget.


Correctness regression always fails regardless of performance gain.

16. GENERATION BENCHMARKS
======================================================================

Procedural generators must distinguish:

COLD:

WARM:
    reusable dependencies/cache populated.

INCREMENTAL:
    only one dependency/subregion changed.

Examples:

    terrain cold generation
    building batch cold generation
    repeat same BuildingPlan artifact lookup
    regenerate one city district after local edit

Do not report warm cache as "generator speed" without label.

======================================================================
18. PRESENTATION BENCHMARKS
======================================================================

Presentation is measured separately from authoritative simulation.

Report:
    extraction time
    changed entities
    transform uploads
    visible representations
    skeletal detailed count
    LOD counts
    draw/dispatch counts
    GPU timings

This preserves the architectural separation from 0.1.

======================================================================
19. STRESS TEST PHILOSOPHY
======================================================================

Stress cases answer:

    how does the system degrade?
    where does it become memory-bound?
    where does scheduling stop scaling?
    what happens at budget limits?
    is failure bounded/graceful?

They are not promises that every stress load is shipping gameplay.

A stress test must not crash merely because a configured representation budget
is reached if the design specifies degradation/demotion.

Example:
    debris capacity pressure should demote/bake according to system policy.

PSEUDOCODE
======================================================================

CPU BENCHMARK:

    function runBenchmark(case, workerCount):
        env := captureEnvironment()

        dataset := case.buildDataset(
            seed = case.seed,
            parameters = case.parameters
        )

        subsystem := case.createSubsystem(workerCount)

        repeat case.warmupIterations:
            case.reset(subsystem, dataset)
            case.execute(subsystem, dataset)

        allSamples := []

        repeat case.repetitions:
            case.reset(subsystem, dataset)

            samples := []

            repeat case.iterations:
                t0 := MonotonicClock.now()
                case.execute(subsystem, dataset)
                t1 := MonotonicClock.now()

                samples.push(t1 - t0)

            case.validate(subsystem, dataset)
            allSamples.extend(samples)

        result := summarize(allSamples)
        result.semanticHash := case.semanticHash(subsystem)
        result.environment := env
        result.workerCount := workerCount

        emitJson(result)


SCALING:

    base := runBenchmark(case, 1)

    for p in supportedWorkerCounts:
        result := runBenchmark(case, p)

        result.speedup := base.mean / result.mean
        result.efficiency := result.speedup / p


REGRESSION:

    function compareBaseline(base, current, policy):
        require base.benchmarkId == current.benchmarkId
        require base.benchmarkVersion == current.benchmarkVersion
        require comparableEnvironment(base, current)

        assert current.correctness == PASS

        delta := current.p95 / base.p95 - 1

        if delta > policy.failureThreshold:
            failRegression(delta)

        if delta > policy.warningThreshold:
            warnRegression(delta)


DETERMINISM:

    canonical := runDeterminismCase(workers=1, scheduleSeed=0)

    for workers in matrix:
        for scheduleSeed in schedulerStressSeeds:
            test := runDeterminismCase(workers, scheduleSeed)

            compareByContract(
                canonical,
                test,
                determinismContract
            )

======================================================================
THREADING / OWNERSHIP RULES
======================================================================

Benchmarking code must not introduce a different ownership/thread model than
production solely to make timing easier.

Instrumentation counters:
    avoid one contended global atomic per inner-loop operation.

Prefer:
    per-worker counters
    end-of-phase aggregation

when measuring hot systems.

Profiler instrumentation overhead should be measured/known for microbenchmarks.

======================================================================
ERROR HANDLING
======================================================================

Benchmark returns non-zero/failure when:

    correctness validation fails,
    dataset construction fails,
    output metadata required by case is unavailable and case requires it,
    determinism comparison fails,
    baseline compatibility check fails.

A performance regression result must never hide a correctness failure.

======================================================================
DETERMINISM RULES
======================================================================

Summary:

    deterministic seed hierarchy
    stable semantic IDs
    stable commit order
    no semantic unordered-container iteration
    no completion-order semantics
    fixed reduction order where exact floating result is required
    worker-count test matrix
    schedule perturbation test where supported

Presentation-only systems may explicitly declare DET-NONAUTHORITATIVE.

======================================================================
PERFORMANCE RULES
======================================================================

Summary:

    optimized build
    no debugger
    same workload
    explicit warm-up
    complete cost
    distributions not only mean
    hardware fingerprint
    scaling matrix
    correctness validation
    memory high-water
    separate CPU/GPU timings
    end-to-end transfer cost for compute

======================================================================
MIGRATION / COMPATIBILITY
======================================================================

Legacy browser benchmarks remain historical reference.

Do not claim direct percentage speedup against a browser number unless the
semantic workload and measured interval are actually equivalent.

Use legacy benchmark primarily to preserve:
    workloads,
    counters,
    invariants,
    known pathological scenarios.

Native benchmark becomes performance authority once its subsystem parity gate
passes.

FORBIDDEN SHORTCUTS
======================================================================

Do NOT:

    benchmark Debug and publish it as production performance;
    compare semantically different workloads as speedup;
    time job submission while draining expensive work later;
    report only average;
    omit worker count;
    omit seed/dataset parameters;
    change RNG dataset between worker counts;
    interpret heap delta as leak proof;
    infer GPU time from CPU submit;
    ignore mandatory GPU readback;
    accept nondeterministic authoritative output because "threads race";
    hash raw structs/pointers/unordered iteration;
    overwrite historical baseline files to hide regression;
    fail to validate output after a fast benchmark.
