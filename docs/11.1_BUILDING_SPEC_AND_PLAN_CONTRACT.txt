======================================================================
PUBLIC CONTRACTS
======================================================================
1. BuildingSpec contains seed path, parcel/buildable polygon, target/use program, floor count/range, target gross area, regularity/complexity/symmetry/circulation parameters, material/roof constraints and optional overrides. It never names a render mesh.

2. BuildingPlan contains stable IDs for footprint, floors, spaces/rooms, circulation, cores, openings, structural panels/elements, roof elements and semantic materials.

3. Every child ID derives from BuildingId + semantic stage/local stable key. IDs cannot depend on vector insertion/completion order.

4. Plan stage metadata records generator version and validation stage; compilers
consume only frozen valid plan.

5. The final catalog uses unambiguous semantic IDs. SMALL_SHED and
RURAL_OUTBUILDING are distinct presets with independently declared dimension,
program and material ranges; no preset changes meaning according to importer or
source file.

6. Room programs, footprint/roof/stair families, structural systems, materials
and seed domains are explicit data tables validated at startup and covered by
the final catalog test matrix.

7. The module consumes city-owned BuildingSiteRequest and returns both a frozen
BuildingPlan and city-facing BuildingSiteResolution. Request fields map to
BuildingSpec without transferring parcel ownership: stable request/parcel ID,
seed path, zone/program constraints, buildable polygon, preferred envelope and
orientation, height/storey limits, and ParcelAccessIntent.

8. BuildingSiteResolution reports BuildingPlanId, resolved footprint,
clearance envelope, entrance/approach point and exterior connection
reservations. The chosen entrance must satisfy ParcelAccessIntent or generation
returns a typed failure/fallback; the city finalizes driveway, gate and fence.

======================================================================
DATA LAYOUT
======================================================================
Building semantic data uses stable IDs, compact arrays and polygons/cells. Render/physics/nav representations are separate compiler outputs.

IMPLEMENTATION STEPS
======================================================================
STEP 1
    Define the final catalog and schema vocabulary: programs, SMALL_SHED,
    RURAL_OUTBUILDING and other presets, footprint/roof/stair families,
    materials, seed domains and validation rules.

STEP 2
    Implement one unified TARGET schema. Reference import/export adapters remain
    outside production types and map evidence into this vocabulary.

STEP 3
    Define enum/data tables for use/program without hardwiring every architectural style into code paths.

STEP 4
    Define local building coordinate system: X/Z footprint plane, Y up, transform to world external.

STEP 5
    Define storey model with floorElevation, clearHeight, slab thickness and vertical connections.

STEP 6
    Define Space/Opening/Core/Structural records with stable IDs and references, not owning pointers.

STEP 7
    Document schema in reference/schemas and add serialization roundtrip.

======================================================================
PSEUDOCODE
======================================================================
CREATE SPEC FROM SITE REQUEST:
    spec.buildingId := derive(request.id,"building")
    spec.seed := request.seedPath
    spec.buildable := request.buildablePolygon
    spec.program := chooseProgram(request.zone,profile,spec.seed)
    spec.targetArea := area(request.buildablePolygon) * seededCoverage
    preserve request access/height/orientation constraints

PLAN:
    plan.header := version/provenance
    plan.spec := normalized spec
    stages fill:
        footprint
        floors
        cores
        circulation/spaces
        openings
        roof
        structure
    freeze only after validation
    resolution := summarizeForCity(plan, request.accessIntent)
    return plan,resolution

======================================================================
THREADING / OWNERSHIP RULES
======================================================================
One BuildingPlan candidate is owned by one job until frozen. Batch jobs are independent by BuildingId/SeedPath and merge in stable ID order.

======================================================================
ERROR HANDLING
======================================================================
Bounded solvers return typed failure/fallback reasons and ValidationReport. Invalid building candidates are never partially committed.

======================================================================
DETERMINISM RULES
======================================================================
Candidate order, tie-breaking and RNG streams are stable by semantic IDs. Worker count and hash-map iteration do not affect the plan.

======================================================================
PERFORMANCE RULES
======================================================================
Use bounded candidate sets, spatial/prefix structures and scratch arenas. No unbounded backtracking. Batch independent buildings over JobSystem.

======================================================================
MIGRATION / COMPATIBILITY
======================================================================
No runtime compatibility schemas or duplicate building generators. TARGET
validators and acceptance tests define final behavior.
