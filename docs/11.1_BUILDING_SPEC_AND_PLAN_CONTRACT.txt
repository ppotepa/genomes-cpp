PUBLIC CONTRACTS
======================================================================
1. BuildingSpec contains seed path, parcel/buildable polygon, target/use program, floor count/range, target gross area, regularity/complexity/symmetry/circulation parameters, material/roof constraints and optional overrides. It never names a render mesh.

2. BuildingPlan contains stable IDs for footprint, floors, spaces/rooms, circulation, cores, openings, structural panels/elements, roof elements and semantic materials.

3. Every child ID derives from BuildingId + semantic stage/local stable key. IDs cannot depend on vector insertion/completion order.

4. Plan stage metadata records generator version and validation stage; compilers
consume only frozen valid plan.

SOURCE schema facts for the audited baseline:
    BuildingSpec:  rts.building-spec/6
    BuildingPlan:  rts.building-plan/4
    RoomGraphSet:  rts.room-graph-set/1
    generator:     building-6.0.0

TARGET may define a new native schema version, but fixture importers must record
which SOURCE schema/version they translate from.

5. SOURCE currently contains overlapping building catalogs/spec systems that
are not fully identical. Native migration MUST NOT silently merge conflicting
values. A SourceCompatibility record is required for any conflicting preset ID.

Known audited example:
    SOURCE::js/buildings/buildingCatalog.js
        RURAL_SHED width 2..3 m, depth 2..3 m

    SOURCE::js/buildings/buildingSpec.js
        RURAL_SHED width 2.5..7 m, depth 2.5..6 m

The TARGET schema must preserve provenance and resolve this explicitly. Preferred
semantic resolution is to separate distinct concepts/versions (for example a
small shed compatibility profile and a larger rural outbuilding profile) rather
than make one ambiguous ID depend on which SOURCE file happened to be read.

6. SOURCE room programs, roof families, stair families, structural systems,
materials and current BuildingSpec seed domains are migration data and must be
enumerated into the v1 schema/parity matrix before implementation is marked
complete.

======================================================================
PSEUDOCODE
======================================================================
CREATE SPEC FROM PARCEL:
    spec.buildingId := derive(parcelId,"building",ordinal)
    spec.seed := citySeed.child("building",buildingId)
    spec.buildable := parcel.buildablePolygon
    spec.program := chooseProgram(zone,profile,seed)
    spec.targetArea := parcel.area * seededCoverage

PLAN:
    plan.header := version/provenance
    plan.spec := normalized spec
    stages fill:
        footprint
        floors
        cores
        circulation/spaces
        openings
        roof
        structure
    freeze only after validation

======================================================================
THREADING / OWNERSHIP RULES
======================================================================
One BuildingPlan candidate is owned by one job until frozen. Batch jobs are independent by BuildingId/SeedPath and merge in stable ID order.

======================================================================
ERROR HANDLING
======================================================================
Bounded solvers return typed failure/fallback reasons and ValidationReport. Invalid building candidates are never partially committed.

======================================================================
DETERMINISM RULES
======================================================================
Candidate order, tie-breaking and RNG streams are stable by semantic IDs. Worker count and hash-map iteration do not affect the plan.

======================================================================
PERFORMANCE RULES
======================================================================
Use bounded candidate sets, spatial/prefix structures and scratch arenas. No unbounded backtracking. Batch independent buildings over JobSystem.

======================================================================
MIGRATION / COMPATIBILITY
======================================================================
SOURCE building systems remain parity/reference. TARGET may improve algorithms if hard invariants and declared parity gates pass.
