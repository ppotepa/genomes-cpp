======================================================================
PUBLIC CONTRACTS
======================================================================
1. KernelId/version uniquely identifies semantic kernel contract. Dispatch contains kernel ID, dimensions, typed parameter block version, input/output buffer views and completion policy.

2. ComputeBackend interface supports capabilities(kernel), dispatch(batch), completion token, optional timeline/fence. CPU backend is mandatory and uses JobSystem.

3. Kernel semantic contract includes exact input/output layout, bounds behavior and determinism class. Backends may differ internally but must satisfy tests.

4. ComputeService chooses requested/preferred backend per kernel based on capability and policy; fallback choice is observable in diagnostics.

======================================================================
DATA LAYOUT
======================================================================
Compute inputs/outputs are explicit buffer/view descriptors with versioned kernel parameter blocks; no backend-native pointer leakage.

======================================================================
PSEUDOCODE
======================================================================
DISPATCH:
    descriptor := registry.find(kernelId)
    backend := policy.choose(descriptor, availableBackends)
    validate layouts/dimensions
    token := backend.dispatch(batch)
    diagnostics.record(backend,kernel,dims)
    return token

CPU BACKEND:
    parallelFor work items:
        kernel.reference(item,params,inputs,outputs)

======================================================================
THREADING / OWNERSHIP RULES
======================================================================
CPU prepares immutable dispatch inputs; backend owns GPU resources and synchronization. Readbacks become visible only after completion tokens/fences.

======================================================================
ERROR HANDLING
======================================================================
Unsupported GPU feature selects explicit CPU/fallback path where allowed; shader/dispatch failures return typed errors and diagnostics.

======================================================================
DETERMINISM RULES
======================================================================
GPU-derived advisory fields may be numerically non-bitwise-identical across hardware; authoritative CPU state cannot depend on undocumented nondeterministic reductions.

======================================================================
PERFORMANCE RULES
======================================================================
Batch dispatches, avoid CPU/GPU ping-pong, measure transfer cost separately from kernel cost and prefer GPU-resident pipelines.

======================================================================
MIGRATION / COMPATIBILITY
======================================================================
TARGET compute service is new infrastructure; SOURCE has no equivalent general
compute layer and remains reference for domain outputs only.
