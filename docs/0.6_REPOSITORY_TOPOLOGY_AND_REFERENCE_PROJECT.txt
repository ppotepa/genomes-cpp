GOAL
======================================================================

Define the product/evidence two-repository model.

SOURCE:
    ppotepa/genomes

TARGET:
    ppotepa/genomes-cpp

SOURCE contains the JavaScript prototype implementation, research, browser labs
and diagnostic tests.

TARGET contains:
    native C++ implementation,
    executable final implementation manual,
    minimal exported reference/validation artifacts,
    native tests,
    native benchmarks,
    native CI.

The two repositories have different responsibilities and MUST NOT gradually
collapse into an accidental duplicate codebase.

======================================================================
PUBLIC CONTRACTS
======================================================================

1. PATH PREFIXES

All manual chapters use:

    TARGET::<path>
    SOURCE::<path>

Unprefixed paths inside implementation sections mean TARGET unless explicitly
stated otherwise.


2. SOURCE REVISION

Every exported fixture/golden/schema must pin exact SOURCE commit SHA.

Never use only:

    SOURCE main

as persistent provenance.


3. TARGET REVISION

Native implementation is versioned normally by TARGET Git history.

A reference-diagnostic report should record:

    sourceCommit
    targetCommit
    fixture/schema version


4. SOURCE ACCESS

An implementation agent may read SOURCE using:

    GitHub connector,
    local separate checkout,
    CI credential with read access,
    explicit export tooling.

TARGET build MUST NOT require SOURCE checkout for normal native compilation.


5. TARGET BUILD INDEPENDENCE

After fixtures required by a chapter have been exported, normal TARGET:

    configure
    build
    unit tests
    deterministic tests

must work without access to the private SOURCE repository.

Only optional reference regeneration/comparison workflows may require SOURCE access.


6. REFERENCE PROJECT

TARGET::reference is a DATA PROJECT, not legacy source mirror.

Allowed:
    compact inputs
    compact semantic outputs
    golden hashes
    selected geometry buffers
    screenshots when explicitly required
    schemas
    provenance
    manifest metadata

Forbidden:
    entire SOURCE js/
    node_modules/
    vendor bundles
    whole research directories copied without purpose
    secret/private operational data


7. SOURCE CHANGES DURING MIGRATION

SOURCE may continue evolving.

A migration chapter must:

    inspect current SOURCE HEAD,
    compare it to its fixture baseline,
    decide whether new SOURCE changes affect that subsystem,
    update fixtures only deliberately.

Do not assume the baseline SHA freezes all future product requirements.


8. REFERENCE BASELINE VS TARGET VALIDATION BASELINE

reference/source/BASELINE.txt:
    initial whole-project migration baseline.

Individual domain fixtures:
    may pin newer exact SOURCE commits.

Example:

    terrain fixture set:
        SOURCE commit A

    building fixture set:
        SOURCE commit B

This is valid if metadata is explicit.


9. PRIVATE SOURCE / PUBLIC TARGET

SOURCE is private at current baseline.
TARGET is public at current baseline.

Therefore:

    never publish SOURCE source files wholesale,
    inspect fixture contents before export,
    export only data intended for public native implementation,
    do not export secrets/user data,
    do not copy private attachments/logs blindly.


10. MANUAL OWNERSHIP

All new native manual chapters live only in TARGET::docs.

Do not author new 1.x/2.x/... native chapters in SOURCE.

If a legacy research document needs correction:
    edit SOURCE legacy doc if it belongs to legacy project.

If a migration instruction changes:
    edit TARGET manual.

IMPLEMENTATION STEPS
======================================================================

For every future domain migration:

STEP 1
    identify SOURCE files/symbols from 0.2 / SOURCE_SUBSYSTEMS manifest.

STEP 2
    record exact SOURCE commit.

STEP 3
    determine TARGET validation class.

STEP 4
    determine whether live SOURCE read is sufficient or persistent fixture is
    required.

STEP 5
    if fixture required:
        export minimal normalized data.

STEP 6
    place in:
        TARGET::reference/fixtures/<domain>/
    or:
        golden/
        schemas/

STEP 7
    add provenance.

STEP 8
    implement C++ in TARGET.

STEP 9
    run native tests without SOURCE dependency.

STEP 10
    run optional diagnostic comparison with SOURCE where useful.

STEP 11
    record sourceCommit + targetCommit in diagnostic result.

        nativeResult := runNative(fixture.input)

        return compare(
            nativeResult,
            fixture.expected,
            fixture.targetValidationPolicy
        )


SOURCE EVOLUTION CHECK:

    function checkSourceEvolution(domain):
        baseline := latestFixtureSourceCommit(domain)
        head := SOURCE.head

        changedPaths := gitDiff(
            baseline,
            head,
            domain.sourcePaths
        )

        if changedPaths empty:
            return NoAction

        return RequiresMigrationReview(changedPaths)

======================================================================
THREADING / OWNERSHIP RULES
======================================================================

Repository topology does not imply runtime ownership.

Reference export tools may execute SOURCE deterministically in one or many
threads according to owning chapter, but exported order must be normalized.

======================================================================
ERROR HANDLING
======================================================================

SOURCE unavailable during normal TARGET build:
    not an error.

SOURCE unavailable during optional reference regeneration:
    regeneration reports SKIPPED / source unavailable; TARGET validation remains runnable.

Fixture missing provenance:
    invalid reference artifact; test/configuration failure.

Fixture references non-existent SOURCE commit:
    invalid reference artifact.

======================================================================
DETERMINISM RULES
======================================================================

Every persistent fixture must be reproducible from:
    exact SOURCE commit,
    exact input,
    exporter version,
    generator/schema version where applicable.

No fixture may depend on current wall time or unordered output serialization.

======================================================================
PERFORMANCE RULES
======================================================================

Do not copy SOURCE into TARGET merely to make parity faster.

Large fixtures require explicit justification.

Prefer:
    compact semantic data
over:
    full generated meshes
when invariants are sufficient.
